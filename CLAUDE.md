# Advising Outreach

A prototype internal tool for a university advising office: advisors see which students to contact next and why, read past advising notes, and log new contacts. Built as a job-application take-home; "today" is fixed at 2026-10-05 per the brief.

## Stack

- Next.js 16 (App Router) · React 19 · TypeScript · Tailwind 4 · shadcn/ui on Base UI (generated by v0, then adapted)
- npm, Node 22.12+ (`package-lock.json` pins versions; dependency install scripts are approved or denied in `package.json` → `allowScripts`, via `npm approve-scripts` / `npm deny-scripts`)
- Database: SQLite file by default (`data/app.db`), Postgres when `DATABASE_URL` is a `postgres://` or `postgresql://` URL. Queries via Kysely.
- CSV parsing: csv-parse · Help pages: react-markdown + remark-gfm · Tests: Vitest (unit), Playwright + axe (end-to-end, accessibility)
- Hosting: GDS deployment 23 (`arizona-prototype`), staging at https://wildcat-staging.glossydevserver.com. GDS runs `npm install` and `npm run build`; its `DATABASE_URL` points at Postgres on the GDS box (reachable only from there). GDS does **not** deploy on push: a build runs only when triggered (glossy-deploy MCP `trigger_build`, or the GDS web UI).

Commands: `npm run dev` · `npm run build` · `npm run typecheck` · `npm run lint` · `npm test` · `npm run seed` (wipe + import the sample data) · `npm run db:reset` (empty; stays empty) · `npm run data:audit` (regenerates `docs/DATA_AUDIT.md`).

Browser tests (first time: `npx playwright install chromium`). Both build first, then run against `next start` on port 3100 with their own database, `data/e2e.db`, so they never touch `data/app.db`. Stop `npm run dev` before running them: it shares `.next/`.
- `npm run test:e2e`: the end-to-end specs and the axe checks (anything worse than "minor" fails) in `e2e/`.
- `npm run docs:screenshots`: walks every screen and saves the help screenshots to `public/help/screens/`. It fails on any browser error along the way. Run it **before** `test:e2e`: `next start` only serves public files that existed at build time, and `e2e/help.spec.ts` checks every screenshot loads.
- `npm run test:responsive`: every page and dialog at 15 widths from 320 to 1279px (`e2e/responsive.spec.ts`), failing on sideways scrolling, anything off the screen, or text spilling out of a control. Saves a screenshot of each to `test-results/responsive-screens/` for review. `test:e2e` runs the same checks at 320, 768 and 1024 only.

Responsive layout rules (T11):
- Page layouts switch on the content area's width, not the screen's: `<main>` is a container, so use `@min-[…]:` variants. The sidebar takes 240px from `md` up.
- A box that scrolls sideways needs `relative`, or screen-reader-only text inside it escapes and widens the page on phones.
- The sheet sets its width under `data-[side=right]:`, so overrides need the same prefix: `data-[side=right]:w-full`, not `w-full`.
The dev machine is Windows/PowerShell 5.1: no `&&` chaining. Commit messages containing double quotes must go through a file (`git commit -F msg.txt`); PowerShell 5.1 splits quoted text when passing arguments to git.

## How we work

- Work in phases (plan in `docs/`, current phase in the latest AI_USAGE_LOG entry). At the end of each phase: stop, summarize, wait for Adam's review.
- Commit at the end of each phase with a conventional commit message.
- Data judgment calls go to Adam with options and a recommendation; don't pick silently. Purely technical choices are ours to make; record them in `docs/DECISIONS.md` (T#).
- Keep the logs current every phase: `docs/AI_USAGE_LOG.md` (what AI did, got wrong, and where a human decided), `docs/DECISIONS.md`, `docs/TIME_LOG.md`.
- Prefer boring, well-known libraries. If something fails, report the error; don't paper over it.
- When the UI changes, update `content/help.md` to match and rerun `npm run docs:screenshots`. `tests/help.test.ts` fails if the help shows a missing screenshot or links to a missing heading.

## Rules for the code

- **Dataset and brief beat the v0 scaffold** (DECISIONS G1). v0 never saw the CSVs.
- **The import never changes data silently** (G2). Every data rule is a named rule with a suggested fix that a person accepts. One decision in DECISIONS.md = one named rule in code, and the rule name appears in the entry. Design: `docs/IMPORT_DESIGN.md`.
- **Never modify `data/source/`.** Those are the hiring team's files, kept byte-for-byte (see `.gitattributes`). The one exception was by them: `README.txt` arrived empty, and on 2026-10-08 it was replaced with the full version they sent (the empty original is in git history). It is the column spec.
- **All data access goes through the service layer** (`lib/services/`). Server components read via `lib/data.ts` (a thin wrapper that opens the shared database); route handlers in `app/api/` validate with Zod and call the same services. Data changes from the browser go through the API, never server actions (the advisor cookie is the one server action: a view preference, not data). API reference: `docs/API.md`.
- **Use `TODAY` from `lib/config.ts`, never `new Date()`,** for anything date-relative (days since contact, overdue, "future" dates). Real timestamps such as `created_at` may use the clock.
- **Portable SQL only** (DECISIONS T2): dates and JSON as text, booleans as 0/1, text IDs; nothing dialect-specific.
- **Never store or display an SSN-shaped number unmasked** (D17), including in logs and the fix history.

## Where things are

- `docs/DATA_AUDIT.md`: what's in the source data (generated by `scripts/audit.ts`)
- `docs/DECISIONS.md`: guiding rules (G), data rules (D), product (P) and technical (T) decisions
- `docs/IMPORT_DESIGN.md`: the interactive import
- `lib/db/`: Kysely client (SQLite or Postgres), migrations, setup (`getDb()` migrates and, on first run only, seeds)
- `lib/import/`: the import engine, all pure functions. `rules/` holds one file per rule (D1–D23)
- `lib/services/`: everything that touches the database (students, notes, data quality, import scan/commit, seed, prototype tools)
- `lib/api.ts`: the API's error shape and helpers; `app/api/`: route handlers
- `app/(app)/`: the app's pages, inside the shell (`layout.tsx`: sidebar, top bar, welcome dialog). The route group doesn't change URLs.
- `app/help/` + `components/help/` + `lib/help.ts`: the help pages, outside the shell. The text is `content/help.md`, split by `##`/`###` headings into the contents list and searchable topics. Screenshots: `public/help/screens/`, made by `e2e/screenshots.spec.ts`
- `e2e/`: Playwright specs (`fixtures.ts` dismisses the welcome dialog and reloads the sample data); `playwright.config.ts`: the `e2e` and `docs` projects
- `app/(app)/import/` + `components/import/`: the step-by-step import (choose a file, check columns, review and fix, done) and the prototype-only panel; it re-checks rows in the browser with the same `lib/import` functions the server uses
- `components/app-shell/welcome-dialog.tsx`: first-visit welcome (P4); the UA logo is only shown from an official file in `public/brand/`
- Testing the UI with browser automation: the automated tab may be in the background, where Chrome pauses CSS animations, so dialogs and panels can look stuck mid open/close. Take a screenshot (which brings the tab forward) before concluding something is broken.
- `lib/scoring.ts`: outreach score and reasons (`WEIGHTS` table), open follow-ups, and the queue order (`compareOutreach`: follow-ups due, then never contacted, then score)
- `lib/contact-preference.ts`: the student's contact preference (P9), the one set of rules used by the import (D19), the Log contact form, the editor and the API
- `lib/types.ts`, `lib/config.ts`: shared types and settings (`TODAY`, reference date via `NEXT_PUBLIC_REFERENCE_DATE`)
- `AGENTS.md` is written by `next dev` itself. Next 16 differs from older versions; its own docs are in `node_modules/next/dist/docs/`, so check there before using an unfamiliar Next API.
